# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Minimalist Bomberman in C++17 (SFML 3, nlohmann_json, GoogleTest). Built with CMake driven by Conan, tasks wrapped in [Taskfile.yaml](Taskfile.yaml). Docs (in French) live in `doc/` (`grid.md`, `character.md`, `engine.md`, `upgrade.md`, `explosion.md`, `bot.md`, `menu.md`, `end_of_match.md`, `network.md`, `sfml.md`); feature specs/prompts live in `prompt/`.

## Commands

Run from the repo root. `BUILD_TYPE` defaults to `Release` (override with `task build BUILD_TYPE=Debug`; the other tasks must use the same value).

- `task install` — exports the locally vendored, patched SFML recipe (see "SFML HiDPI patch" below), then `conan install` (dependencies; needed before the first build)
- `task build` — `conan build .`: configures, compiles **and runs the tests** (`cmake.test()` in `conanfile.py`). Skip tests with `conan build . -c tools.build:skip_test=True`
- `task test` — `ctest --test-dir build/Release --output-on-failure`
- Single test: `ctest --test-dir build/Release -R <regex> --output-on-failure` (or run `build/Release/bin/grid_tests --gtest_filter=Suite.Case`)
- `task coverage` — GCC/Clang only (`BOMBERMAN_COVERAGE` fails on MSVC); gcovr report in `build/Release/coverage`, line/function/branch percentages printed at the end
- `task conan-all` = install + build + `export-pkg`; `task consume` installs the packaged result with `VirtualRunEnv` into `env/`

Running the game: the executable loads `$BOMBERMAN_ROOT/data/grid/level_01..04.json` (or `./data/...` if unset) for the menu's map row; a level path passed as first argument is offered first; `--join <address>[:<port>]` joins a network game at once (see "Network multiplayer" below). Binaries and DLLs all land in `build/Release/bin`. `exe/main.cpp` always launches fullscreen at the desktop resolution: the tile size is derived from `sf::VideoMode::getDesktopMode()` (the smaller of width/height divided by the grid's dimensions) so tiles stay square and the grid is centered via a `sf::View`; there is currently no windowed/resizable mode.

The game opens on the **launch menu** (`MatchSetupRenderer`, see `doc/menu.md`): one row per setting (mode = solo / host / join, pirate, map, bot difficulty, number of opponents 1–3; rows the mode does not use are shaded and skipped, `MatchSetup::isRowActive()`); `Z`/`S` or up/down pick the row, `Q`/`D` or left/right change it, `Enter`/`Space` starts the match (solo) or opens the waiting room (host) or the search screen (join), `Escape` quits; in a solo game `Tab` comes back to it, and a finished match returns to it after its end screen (see "End of match" below). The key that started the match must be released before the keyboard drives the player (`waitForRelease` in `exe/main.cpp`, otherwise `Space` would drop a bomb at once). In game: `Z`/`Q`/`S`/`D` to move (immediately, no turning step first), `Space` to drop a bomb **where the character stands** (it can step off it but not back on it), `Enter` to push the bomb standing in front of the character (it does nothing otherwise; to face a bomb, press towards it: a blocked move only turns), `1`–`4` to restart on `data/grid/level_01..04.json` with the same setup (solo only; `exe/main.cpp` rebuilds the whole `Match` — engine, bots, renderers), `Escape` to quit.

## Architecture

- `lib/<name>/` — one **shared library** per folder, sources in `src/`, target `Bomberman::<name>`. Currently:
  - `grid` (logic: `Position`, `Tile`, `Grid`, `GridLoader`; no SFML dependency, so it is testable without a window)
  - `character` (logic: `Character`, `CharacterCommand`, `Direction`; depends on `grid` only)
  - `bomb` (logic: `Bomb`, `Blast`, `BombManager`; depends on `grid` + `character` for `Direction`/`step`)
  - `upgrade` (logic: `UpgradeType`/`Upgrade`, `UpgradeRules`, `PlayerStats`, `UpgradeManager`, `Random`; depends on `grid` only)
  - `engine` (logic: `GameEngine`, `GameRules`, `GameEvent`, `FixedTimestep`, `PlayerController`, `MatchReferee`; depends on `grid` + `character` + `bomb` + `upgrade`, no SFML)
  - `bot` (logic: `BotDifficulty`/`BotProfile`, `DangerMap`, `ReachMap`, `Bot`; depends on `engine` and below, no SFML; see "Bots" below and `doc/bot.md`)
  - `network` (`HostSession`, `ClientSession`, `Lobby`, `Connection`, `DiscoveryBeacon`/`DiscoveryListener`, `TickPlayout`, protocol in `protocol.h`; depends on `engine` and below + `SFML::Network`, never on `render`: crew models travel as indexes in `AllCharacterModels`; see "Network multiplayer" below and `doc/network.md`)
  - `render` (SFML: `Mesh`, `GridRenderer`, `MapTheme`, `CharacterModel`, `CharacterRenderer`, `CharacterSelectRenderer` (former launch screen, no longer used by `exe/main.cpp`), `MatchSetup`/`MatchSetupRenderer` (launch menu), `LobbyRenderer` (network waiting room), `DiscoveryRenderer` (search for a network game), `MenuArt` (drawings shared by those three screens), `GameOverRenderer` (end screen), `BombRenderer`, `UpgradeRenderer`, `DangerZoneRenderer`, `ExplosionRenderer`, `KeyboardController`; depends on `grid` + `character` + `bomb` + `upgrade`, never on `engine`, `bot` nor `network`: the menu's difficulty is an index into `AllBotDifficulties`, converted in `exe/match.cpp`)
  - `lib/cpp_template` is a skeleton that is not wired into CMake.
- `exe/` — the `bomberman` executable: `main.cpp` chains the screens (`Menu` → [`Search` →] `Lobby` → `Match` → …) and owns the network sessions; `match.{h,cpp}` builds a `Match` (`MatchRole` Solo/Host/Client: engine + renderers + referee), presents a frame's events (`presentFrame()`) and draws it with the end screen (`drawMatch()`). `tests/<name>/` mirrors `lib/<name>` (one GoogleTest executable per lib, e.g. `grid_tests`).
- `data/` — level JSON files (format described in `doc/grid.md`); packaged by Conan and exposed through `BOMBERMAN_ROOT`. Tests get the source `data/` via the `BOMBERMAN_DATA_DIR` compile definition.
- Engine (see `doc/engine.md`): `GameEngine` owns the `Grid`, the `BombManager` and every character, and runs the match in fixed ticks (`GameRules::tickRate` = 60 Hz, `FixedTimestep` accumulator, at most 5 ticks per frame after a freeze). It is the only thing `exe/main.cpp` drives: `addPlayer()` (next unused spawn point → `PlayerId` 0, 1…, also the bombs' owner id), `submitCommand(id, command)` (keyboard, or a network client's keys on the host), `setController(id, std::unique_ptr<PlayerController>)` (bots: the engine itself asks `decide(engine, id)` at step 1 of every tick where that player is ready, so bots are frame-rate independent; a controlled player ignores `submitCommand`, `nullptr` gives it back), `advance(realSeconds)` (or `tick()` in tests), then `takeEvents()` (`PlayerTurned`/`PlayerMoved`/`BombPlaced`/`BombPushed`/`Explosion`/`PlayerKilled`/`UpgradeSpawned`/`UpgradeCollected`/`UpgradeDestroyed`, stamped with the tick; one `Explosion` per exploding bomb, with `position` = its center, `blast` = its `Blast` and `cells` = `blast.cells()`; `GameEvent::upgrade` holds the type for the upgrade ones) to drive renderers. Each player has `PlayerStats` (`getStats(id)`: `maxBombs`, `pushDistance`, `blastRadius`, starting from `GameRules::startingStats` = 1/1/1) used for every bomb it places/pushes; upgrades raise them (see Upgrades below). Pacing: after a successful action the player is busy for `moveTicks` (10, also the walk duration given to `Character`), `turnTicks` (5), `placeBombTicks`/`pushBombTicks` (15); failed actions cost nothing; commands arriving while busy are **dropped**, never queued, but a command submitted before `advance()` stays pending for every tick of that call (so a low frame rate doesn't miss the ready tick). Tick order: commands (players by id; a controller sees the actions of lower ids) → alive players pick up the upgrade on their cell (so as soon as a move starts) → `Character::update` + cooldowns → `BombManager::update` (emits `Explosion`, destroys upgrades on hit cells, spawns upgrades in the blocks it destroyed — spared by that same explosion — then kills players on hit cells). The engine enforces that dead players ignore commands. Keep all delays in whole ticks (determinism across frame rates is tested). `Character::update` and `Bomb::update` snap to the end when within `TimeTolerance` (1e-4 s) so tick sums land exactly (a 2 s fuse = 120 ticks).
- Character: `Character` moves cell by cell and is driven **only** through `CharacterCommand` (`move(dir)` / `pushBomb()` / `placeBomb()`) via `Character::execute(command, grid, obstacles = {})`, which takes the grid as `const`: a character never breaks blocks (game rule: only bomb explosions destroy them). Bombs block movement: since `character` cannot depend on `bomb`, callers pass `BombManager::getBombPositions()` as `obstacles` (only the target cell is checked, so a character can always step off a bomb). `execute()` returns `false` for both bomb commands since they need a `BombManager`, which `Character` does not know about — `GameEngine` handles them: `placeBomb` on the character's own cell, `pushBombAt` on the faced cell (`step(character.getPosition(), character.getFacing())`). Keyboard (`KeyboardController`, default z/q/s/d + Enter + Space), future AI and future network input must all just produce commands; never put input or SFML in `character` or `bomb`. Time is injected with `update(dt)`: a move changes the logical position immediately, then the character is busy for `moveDuration` (new commands ignored) while `CharacterRenderer` interpolates `getPreviousPosition()` → `getPosition()` with `getMoveProgress()`. Moves are immediate: `move(dir)` faces `dir` and steps there at once if the cell is free (returns `true`); towards a blocked cell (wall, block, bomb) it only turns (returns `false`), which is how a player faces a bomb to push it. The engine charges `moveTicks` for a step, `turnTicks` for a turn towards a blocked cell, nothing when nothing changed. Holding a key keeps walking (the keyboard submits the command every frame). In tests, `walk()` steps one cell and `face()` turns towards a blocked cell (`tests/engine/game_engine_test.cpp`). Whenever the grid changes (only on an `Explosion` event), the caller must call `GridRenderer::update(engine.getGrid())` (back/front sync). `Character::kill()`/`isAlive()` track death (set by `GameEngine` when the character's cell is in a bomb explosion's hit cells); a dead character is not drawn, and `GameEngine` stops executing its commands, but `Character` itself does not enforce this. `exe/main.cpp` adds the keyboard player on the first spawn point, then one `Bot` per opponent chosen in the menu on the next ones. Network multiplayer: see below; local (same keyboard) multiplayer is not implemented.
- Bombs: `Bomb` is pure data (position, fuse countdown, blast radius) with `update(dt)`/`hasExploded()`. `BombManager` owns the collection: `placeBomb(position, grid, ownerId = 0, maxActiveBombs = DefaultMaxActiveBombs, blastRadius = Bomb::DefaultBlastRadius)` fails if the cell is not walkable, already has a bomb, or `ownerId` already has `maxActiveBombs` unexploded bombs (default 1: one active bomb per character; each `Bomb` stores its `getOwnerId()`, which `GameEngine` sets to the `PlayerId`); `countActiveBombs(ownerId)` gives the current count; `pushBombAt(position, direction, grid, distance=1, obstacles={})` makes a bomb **slide** up to `distance` cells, stopping before the first non-walkable cell, other bomb or obstacle (the engine passes the other alive players), and returns where it landed (`std::optional<Position>`, empty if it could not move at all) — what `PushBomb`/`Enter` does through `GameEngine`; `update(dt, grid, destroyedBlocks = nullptr, blasts = nullptr)` advances every fuse, explodes the ones that reach zero, one after the other (destroying destructible blocks in a cross, stopping at the first wall or destroyed block per arm; destroyed blocks are appended to `destroyedBlocks`, each explosion's `Blast` to `blasts`) and returns every cell an explosion touched (bomb center included) so the caller (`GameEngine`) can kill any character standing there. Bombs do not trigger each other (no chain reaction). `Blast::compute(center, radius, grid)` is the **single** rule for an explosion's shape (center + `reach` per arm, indexed like `Blast::Directions` = Up, Down, Left, Right: stops before walls/the edge, includes the destructible block it hits; computing never modifies the grid): `BombManager` applies it, `DangerZoneRenderer` previews it — never duplicate that walk elsewhere. The bomb is dropped on the character's own cell: the character can step off it (only the target cell is checked) but not come back before it explodes. Defaults: `Bomb::DefaultFuseDuration` = 2s, `Bomb::DefaultBlastRadius`/`BombManager::DefaultPushDistance` = 1 cell, `BombManager::DefaultMaxActiveBombs` = 1; the engine passes the placing/pushing player's `PlayerStats` instead.
- Upgrades (see `doc/upgrade.md`): entities on top of the grid (`Upgrade{position, type}`), never tiles, never blocking movement, bombs or blasts. `UpgradeManager` (owned by `GameEngine`, exposed via `getUpgrades()`/`addUpgrade()`) spawns them in destroyed blocks: `roll()` = `UpgradeRules::dropChancePercent` (25) then a type by `weights` (1/1/1 → a third each). Picking one up calls `PlayerStats::apply(type, rules)`: +1 `maxBombs` (cap 8) / `pushDistance` (cap 5) / `blastRadius` (cap 8); at the cap it is consumed without effect. A bomb keeps the radius its owner had when placing it. Randomness goes through `Random` (SplitMix64 seeded by `GameRules::seed`), never `<random>` distributions (implementation-defined output): the same seed + commands must give the same game on every platform (the first outputs are pinned in `random_test.cpp`). `spawnInDestroyedBlocks` draws once per destroyed block even when it cannot place the upgrade, so the draw sequence only depends on the blocks. Tests force drops with `dropChancePercent = 100` and a single non-zero weight.
- Bots (see `doc/bot.md`, the user asked for it to stay complete): `Bot` implements `PlayerController` and answers with ordinary `CharacterCommand`s. Each decision: `Bot::perceive()` builds a `DangerMap` (per cell, the sorted ticks at which an explosion hits it, tick 0 = the tick being run; `freeFrom` = when a bomb/block cell opens; computed by replaying the bombs on a grid copy with `Blast::compute`, in `BombManager::update` order — keep it exact, `PredictionsMatchTheBombManager` checks it tick by tick; other players' bombs are only noticed after `reactionTicks`, unnoticed ones still block their cell), then `ReachMap::explore(danger, start, delay, moveTicks)` (time-expanded search over `(cell, ready tick)`, every step costs `moveTicks` since moves are immediate, waits only until a neighbouring event, plain Dijkstra after `getCalmTick()`; the start cell may hold the bot's own bomb: it can step off, not come back; result = earliest tick to stand on a cell *for good* + `firstStep`; `Scope::UntilSafe` stops at the first safe cells). Rules in order: escape (push the faced bomb onto an opponent for hard bots, else `nearestSafeCell`, else push a bomb away) → idle/hesitate → drop a bomb where it stands if `bombValue` > 0 and `canEscapeAfterPlacing` (simulated on a `BombManager` copy; hard bots also survive every opponent within `anticipationRange` dropping one where it stands) → best goal by `value * 1000 / (travel ticks + 20)` (upgrades, cells to bomb from; trap check on the top 3 for hard bots) → hunt or wander. Difficulty = `BotProfile::forDifficulty` only (same brain). Bots draw randomness from their own `Random` (seeded per bot): never `<random>` distributions. Keep a decision cheap (4 hard bots: median 10 µs per tick); `BotMatchTest` pins determinism, frame-rate independence and hard > easy in duels.
- End of match (see `doc/end_of_match.md`, validated mock-up "Fin de l'abordage"): `MatchReferee(human, rule)` (engine lib, pure logic; `update(engine, dt, events)` decides tick by tick from the frame's `PlayerKilled` events: over at the first tick with ≤ 1 alive, so host and clients agree whatever their frames; `SpectatorRule::RealTime` in network games = no speed-up nor time limit) gives `gameSeconds(realSeconds)` to pass to `advance()` — normal while `Playing`, ×`SpectatorSpeed` (4) while `Spectating` (human dead, 2+ opponents alive, at most `SpectatorTimeLimit` = 30 real s, then a draw), 0 once `Over` (≤ 1 alive; `getWinner()` = the survivor, nothing for a draw). `exe/main.cpp` calls `triggerDeathAnimation()` on `PlayerKilled` and keeps drawing a dead character while `isDying()` ("Carbonisé", `CharacterRenderer::DeathDuration` = 1.3 s: flash ×2.2, charred to 18 %, shaking, squashed onto its soles, ashes + grey smoke, mock-up `hash(i, salt)` reproduced). Once over, after `DeathDuration` it starts `GameOverRenderer` (`MatchOutcome` Victory/Defeat/Draw, winner model + palette) and draws it with its own `viewFor()` over the frozen board for `Duration` = 3 s, then back to the menu. `GameOverRenderer` ("Le pavillon noir"): darkening (also over the bars), waving black flag with opaque crossed bones, GAME OVER letters drawn as round strokes (glyphs G A M E O V R in a 70x100 box, ink 30 + fill 16; gold for a victory, bone otherwise) dropping one by one, spotlight, open overflowing chest ("Le coffre débordant") popping with `easeOutBack` (scaled, never faded: group opacity would show overlaps), the winner standing in the gold with a crown (skull for a draw), falling coins for a victory. Coordinates are the mock-up's (1600x900).
- Network multiplayer (see `doc/network.md`, the user validated each choice; validated mock-up "Rassembler l'équipage", proposal A): 2–4 humans on the same LAN, no bots. **Host-paced lockstep**: only the host runs the match with authority (`GameEngine::setCommandRecording(true)`), submits its clients' held commands like local keys (`HostSession::takeCommand()`: held, or the last tap until read), and after each frame sends `Ticks` = the commands executed per tick (`makeTickFrames()`) + every `ChecksumInterval` (60) ticks its `stateHash()`; clients never call `advance()`: `TickPlayout` buffers the ticks and replays them at 60 Hz (`applyTickFrame()` = submit + `tick()`, catch-up above `MaxBacklog` = 4) and compares the hashes (a desync is logged, not corrected). Everything stays deterministic: keep simulation floats free of FMA (`-ffp-contract=off` in `cmake/CommonMacros.cmake`), never send state, never let a client tick on its own. TCP via `sfml-network` (`Connection`: non-blocking, outgoing queue, closes on malformed packets or a peer that stops reading), port 53790 (another free one if taken, announced); discovery = UDP broadcast `Beacon` on 53791 every 0.5 s while in the lobby, `--join` fallback. `StartMatch` carries full `GameRules` (seed) + the grid + players (seat → `paletteForPlayer(seat)` color, model index); PlayerId = rank of the taken seat, the host is seat 0 / player 0. A client leaving mid-match leaves its pirate idle; the host leaving sends everyone back to the menu; after the end screen everybody returns to the waiting room (`Tab` of the host: `BackToLobby` at once). `Lobby` = pure seat logic (unique models, seat count = map spawn points). Screens: `LobbyRenderer` (4 seat panels with pennant/dots/crown, ghost outline + waiting dots for free seats, pop-in of newcomers, map miniature, waves, lanterns, launch button or hourglass) and `DiscoveryRenderer` (night sky, sweeping spyglass, 3 host cards per page, miniatures cached by host key). Tests: `tests/network` (real loopback sockets, a full match replayed identically by two clients).
- Design intent: tiles are static cell content only; players/bombs/bonuses are separate entities positioned via `Position` with their own renderers drawn over `GridRenderer`.

### Rendering notes

- Maps: each level JSON has an optional `"theme"` string (stored as-is by `Grid::getTheme()`, never interpreted by `grid`); `mapThemeFromName()` turns it into a `MapTheme` (`Deck`, `Island`, `Cave`, `Docks`, unknown → `Deck`) passed to `GridRenderer`. `GridRenderer::update()` tessellates the whole board (themed floors, light grid lines on playable cells, themed border walls vs inner pillars, the shared cargo crate for every destructible block, island foam, cave torches) into **one** `sf::VertexArray` of triangles: no textures and no GL context needed to build it (tests inspect the vertices headless), one draw call per frame. Per-cell variation uses a deterministic hash (`noise(x, y, salt)`), so rebuilding after a crate is destroyed doesn't reshuffle the floor. The crate drawing doesn't depend on the theme, keep it that way so new maps reuse it. Everything must stay inside the board (`ShippedLevelsStayInsideTheBoard` test), since the fullscreen margin around it is black.
- `Mesh` (`lib/render/src/mesh.h`) is the shared tessellator used by `GridRenderer` and `CharacterRenderer`: shapes are appended as triangles to an `sf::VertexArray` (convex/star/ear-clipped polygons, ellipses with radius-based segment counts, SVG-like strokes centered on the path with round joins). Prefer it over `sf::Shape` for new artwork: `sf::CircleShape` defaults to 30 sides (faceted in fullscreen) and `sf::Shape` outlines produce long miter spikes on thin/pointy shapes.
- `CharacterRenderer` rebuilds its vertex array every `update()` from the exact coordinates of the validated mock-up (100x100 view box, body circle centered on (50, 56) with radius 27, mapped so that radius = 0.33 tile); the right profile is the left one mirrored. Keep the head cluster attached to the body (no per-facing offset), otherwise the bandana slides off the head. The artwork changes with `Character::getFacing()` — facing down is the full front view (bandana, one eye, eyepatch+strap, scar, blush, smile); facing up shows the back of the head only (no face, the bandana covers almost all of it); facing left/right show a side profile (single centered arm/leg/ear, eye+scar on the leading side, eyepatch hidden since it's on the far cheek). `triggerBombAnimation()` plays a short arms-up pose with a ground spark; call it once `BombManager::placeBomb` succeeds. `CharacterRenderer::Palette`/`paletteForPlayer(0..3)` give 4 preset bandana colors (skin stays identical) for the future multiplayer mode; only tests use `paletteForPlayer` so far, `exe/main.cpp` uses the default palette (player 0, red).
- Character models (validated mock-up "Équipage du galion", see `doc/character.md`): `CharacterModel` (`character_model.h`, purely visual, `AllCharacterModels` is the selection order) = `Buccaneer` (the original above), `Captain` (gold-trimmed tricorne with a skull, handlebar mustache), `Lookout` (striped beanie, pompom, freckles), `Parrot` (green body, wings, beak, crest drawn behind the body, tail feathers behind the arms, orange feet), `Revenant` (skeleton, glowing sockets, dark bandana reusing the buccaneer's bandana shapes), `Spaniel` (validated mock-up "Le chien du bord", proposal A: chocolate and tan cocker, tan legs, long wavy ears hanging outside the head — shifted 5 units outwards on the front/back views, the near ear 38 units right on the profile —, red polka-dot neckerchief, a tail drawn before the arms like the parrot's that wags all the time, `sin(t·2π·2)·14°`, with an internal `m_elapsed` clock). All share the same template (legs → [parrot/spaniel tail] → arms → [parrot crest] → body → head/face) so every animation works for all; only `update()`'s per-model switch differs. The palette skin applies to the human models, the bandana color to the Buccaneer only. `setBrightness()` multiplies every vertex color (used to dim the pirates not selected). Mock-up SVG paths are ported with the `path(start, {{control, to}, ...})` helper (a straight `L` = a quad whose control is the midpoint).
- **Translucent thin strokes are forbidden**: a stroke is tessellated as overlapping segments + round joins, so a color with alpha < 255 draws darker dots where they overlap. Use the opaque color the mock-up's translucent ink gives over the stroke's background (e.g. `Rib`, `FeatherLine`, `Crack`, the upgrade arm's `Knuckle`); translucency is fine for single filled shapes (ellipses, polygons). `CharacterModelTest.ThinStrokesAreOpaque` guards the new models.
- `MatchSetupRenderer` (launch menu, validated mock-up "Préparer l'abordage", layout "Le tableau de bord", published artifact) lays the menu out in a 1600x900 design space (`viewFor(screenSize)` fits it with black bars), coordinates copied from the mock-up: deck planks, one rounded panel per `MatchSetup::Row` (`rowBounds()`, gold frame on the focused one), a golden badge per row (swords, bandana, compass, skull, two skeletons), mode icons (`ModeX` = 420 + 400·i: buccaneer vs revenant / ship with the crowned buccaneer on its sail + waves / spyglass + waves, shared drawings in `MenuArt`), rows inactive for the mode shaded by a 45 % black rounded rect in front, the 6 crew models (`PirateX` = 335 + 215·i; others dimmed at size 150, the chosen one at size 190 hopping `|sin(t·π·1.6)|·18` in a golden ring), map miniatures (real `GridRenderer`s fitted in `MapSlotSize`, unselected ones dimmed by a 40 % black rect, 4 per page), difficulty pennants (1–3 skulls on green/orange/red), opponent counts (each in its own wooden slot, with dots), and the launch button (grey when `!canStart()`). It positions plain `CharacterRenderer`s (tile size = size/100·27/0.33, moved with `setPosition`), the chosen pirate last. No text anywhere: the project ships no font. `CharacterSelectRenderer` (the former pirate-only launch screen, same placement technique) is kept but no longer used.
- `UpgradeRenderer` (one vertex array for every upgrade, via `Mesh`) reproduces the validated mock-up (published artifact "Butin des caisses"; choices: ExtraBomb = small lit bomb + golden "+" badge, PushStrength = flexed tattooed arm in the crew's skin with the red bandana wristband, BlastRadius = cartoon burst; socle = floating over a shadow with a twinkling star). Coordinates are a 100x100 view box per **cell** (origin at the cell's top-left, unlike `CharacterRenderer`'s body-centered space); the item group is `translate(9 5) scale(.82)` and bobs up to `BobAmplitude` (3.5 units) with a `AnimationPeriod` of 1.6 s, the shadow stays on the floor. `exe/main.cpp` updates it every frame with `engine.getUpgrades()` and draws it after the grid, before bombs and the player.
- Explosions (validated mock-up "Souffle des bombes", see `doc/explosion.md`): `exe/main.cpp` feeds each `Explosion` event's `blast` to `ExplosionRenderer::add()` and calls `update(dt)` every frame; it is drawn last (over the player). Style `Fireballs` is the one in game (a chain of fireballs popping 0.05 of the timeline per cell, turning to smoke from u = 0.55); `FlameCross` (continuous four-layer cross) is kept on purpose for a future feature: don't delete it. Each explosion lasts `Duration` = 0.6 s and fades out from u = 0.6 **as a whole** (the mock-up's group opacity): `draw()` renders a fading explosion opaque into a lazily created `sf::RenderTexture` (sized to its bounds, AA capped to `sf::RenderTexture::getMaximumAntiAliasingLevel()` — only 4x on some Macs, asking for 8x made `resize()` fail and the explosion vanish; per-vertex fade as last-resort fallback) and blends that, because per-vertex alpha would show the ink outlines through the fire. Tests only check the vertices (no GL context); the opacity is exposed through `getOpacity(i)`. `DangerZoneRenderer` tints in red (rounded square inset 5/100, radius 10) the `Blast::compute` cells of every ticking bomb, opacity `0.10 + 0.22 * progress + 0.08 * pulse` with a pulse speeding up with the fuse; drawn right after the grid, under upgrades/bombs/characters. Draw order in `exe/main.cpp`: grid → danger zone → upgrades → bombs → characters (by `PlayerId`, alive only) → explosions.
- `BombRenderer` still uses `sf::Shape`s (body circle with a `Mesh::segmentsFor()` point count, a fuse as a rotated rectangle, a spark); the spark blinks faster and the body pulses faster as `Bomb::getTimeRemaining()` runs out.
- Never size anything in fixed pixels: `tileSize` depends on the screen (see "Commands"), so lengths and stroke widths are fractions of the tile (`GridRenderer`, `BombRenderer`) or mock-up units scaled with it (`CharacterRenderer`), with a 1 px minimum. The window also requests 8x anti-aliasing.
- Adding a map: drop a `data/grid/level_0N.json` with a `"theme"`, then add it to the `ShippedLevelTest` list (`tests/grid/grid_loader_test.cpp`), the theme/level checks in `tests/render/grid_renderer_test.cpp`, and bump `LevelCount` + `levelKeys` in `exe/main.cpp`. A new look means a new `MapTheme` value with its floor/border/pillar painters in `grid_renderer.cpp` (reuse `crate()` as is).

### SFML HiDPI patch

SFML 3.0.2's macOS backend hardcodes `highDpi:NO` (`SFWindowController.mm`), so on a Retina display the game renders at the non-Retina logical resolution and gets blurrily upscaled by the OS — this is **not** fixable from application code (no public SFML API toggles it). `conan-recipes/sfml/` vendors the upstream conan-center recipe for `sfml/3.0.2` with an extra patch (`patches/3.0.2-002-macos-highdpi.patch`) flipping that flag to `YES`. `task export-sfml-recipe` (run automatically by `install`/`coverage`/`consume`) registers this recipe in the local Conan cache before `conan install`, so a clean cache still ends up with the patched SFML without manual steps. If SFML is ever upgraded, re-check whether upstream fixed HiDPI support before re-applying this patch.

### CMake conventions

Targets are created with the macros in `cmake/` (`bomberman_add_library`, `bomberman_add_header_only_library`, `bomberman_add_executable`, `bomberman_add_test`), not raw `add_library`. Sources are **globbed** (`CONFIGURE_DEPENDS`) from `src/` (or next to the CMakeLists for exe/tests), so adding a file needs no CMake edit; use `EXCLUDE` to leave one out. A new lib/test folder needs an `add_subdirectory` in the parent `CMakeLists.txt`.

### Windows/DLL gotchas

- Libraries are shared by default and `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS` is on, so no `__declspec` markup is needed.
- SFML **must** stay `shared` (`conanfile.py` default option): `render.dll` exports all symbols, a static SFML would be duplicated in each consumer.
- Tests use `gtest_discover_tests(... PRE_TEST)` so building never requires the DLLs to be loadable.
- `Taskfile.yaml` must stay valid UTF-8 (a Latin-1 accent makes `task` refuse to parse it).
- Warnings are on (`/W4` or `-Wall -Wextra`). Floating-point contraction is off (`-ffp-contract=off`, MSVC `/fp:precise`) for cross-machine determinism of network games.
